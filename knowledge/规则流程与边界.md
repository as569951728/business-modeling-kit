# E3 规则、流程、范围与未知怎样写清楚

前置：K7–K9、E2。本章解释从业务说法到可核查模型表达的转换；不直接生成数据库或指标代码。

## 把一条规则写完整

采用“在什么范围和时间，对哪个对象，满足哪些条件时，得到什么判断／应作什么处理；有哪些例外，依据在哪里”的句式。

逐项核对：条件是同时满足还是任选其一？判定作用于同一对象／事件还是一个集合？不满足的结果是否已说明？例外覆盖哪一条规则？时间端点如何处理？每个答案都需材料支持，不从语言流畅推断规则完整。

例：假设材料只说“完成检查后可以提交复核”。它说明一个前置条件或流程许可，不能推出“完成检查后一定已经复核通过”，也不能推出“未检查绝对不能在任何情况下提交”，除非材料明确排除了例外。

## 三类状态不要混写

- 业务状态：某单据已经完成。
- 证据状态：目前只有经手人口头说明，尚未核对原记录。
- 工作状态：FDE 已把候选写入草稿，尚待采用。

AI 生成了草稿，不会改变客户业务状态，也不会自动加强原始证据。

## 流程的最小表达

沿一件真实工作写：触发 → 参与者 → 使用的材料 → 动作与判断 → 留下的结果 → 交接与反馈。正常、退回、取消、补录等分支按实际资料补充，不列成所有客户必有的环节。

区分规定流程和实际做法。若材料说“通常先电话确认，再补记录”，不要自动修成理想流程；先说明它是实际做法、适用范围和待核制度。

## 五种边界怎样分开

| 边界 | 应回答什么 | 由什么支撑 |
| --- | --- | --- |
| 任务范围 | 本轮为谁解释什么、哪些暂不做 | 项目目标和具体使用任务 |
| 规则适用范围 | 哪些对象、时间、地区或场景适用 | 规则说明、记录及有职责的确认 |
| 数据与结论范围 | 这批记录覆盖什么、不能推出什么 | 数据来源、粒度、覆盖与质量检查 |
| 动作权限 | 允许谁做什么、是否只是候选需求 | 对具体操作的实际授权和系统能力 |
| 验证与交付范围 | 做了哪些检查，谁认可哪些成果 | 实际输入输出、判读与确认记录 |

这些边界互相引用，但不能互相替代。例如“可以展示 Demo”不自动等于“可以修改客户生产数据”；“能解释一个实例”不自动证明所有月份都正确。

## 不同说法怎样处理

先对齐说话人的实际职责、对象、时间、范围与词义。两种说法可能都是局部事实，也可能是规则更新、操作偏差或真实冲突。暂时不能判断时并列来源，说明影响哪条模型定义和什么任务，再列需要的证据及联系人。

未知不等于禁止；未见记录不等于事件没有发生。对已有依据的部分继续建模，把受缺口影响的结论限定住，不把整个项目一律阻塞。

## 用正反例查规则

对适用条件成立、条件不成立、条件未知、边界时间或例外各选有意义的实例。只有在资料已经明确时，才能决定应得结论；否则检查模型能否准确说明未知。

模型中的规则需要计算时，把它连到后续指标定义和独立核算；模型说明本身不证明实现算对。

## 学完要能做到什么

把本项目一条关键规则写成完整句，指出其作用对象与范围；说明一个适用例、一个不能直接推出结论的例子。再把实际流程和 FDE 自己的实施步骤分开保存。
