# 让 AI 实现测试集、独立期望与判定

承接 [13](13-指标库建立手册.md)的 M2／M5。用户提供任务和原始材料，AI 负责出题、核算、实现、执行与记录；FDE 核关键业务规则、代表性明细与取舍。无需用户手填全部 expected 或手写 judge。使用[测试与验收模板](../../templates/指标测试与验收.md)，先看[完整示范](../../examples/维修指标-完整示范.md)。

## 先检查测试本身是否合格

指标实施按 [13](13-指标库建立手册.md)的主动核对点执行：M2 先准备完整测试设计和代表性独立核算，解释明细为何计入／排除，再请本人核对；不能让用户从空白表开始，也不能因生成了 expected 就默认本人已核。正常、边界和未知情形按本项目选，不要求本人手算全部用例。技术自检由 AI 完成，本人核对和 judge 自检分别记录；未取得本批必要回复，不越过核对点开始依赖它的构建或系统测试。

这是本章方法的统一检查入口。先确定项目范围、已核规则及适用接口，再按下表复核已有测试；不只按固定题数打分。用户看结论、关键缺口和需本人判断的事项，明细由 AI 维护在原测试记录。

| 标准 | 按什么判断与取证 |
| --- | --- |
| 有依据 | 每项测试对应本轮任务与已核业务规则，能定位到原件及适用条件；假设、冲突和未决行为另列，不能拿实现结果作业务依据 |
| 覆盖重点 | 原始规则与用例双向对应；按实际风险覆盖正常、边界、逆向／未知、粒度关联和问法等，列未覆盖项；同义题不能代替规则覆盖 |
| 答案独立 | expected 来自固定原始记录与已核口径，有计入排除明细或独立核算；不抄 actual、不复用待测生成 SQL，关键样本按项目约定复核 |
| 能抓错 | 说明关键风险对应的错误实现，证明所选数据会令正确与错误结果不同；碰巧相同的总数不够。推导与实际错误注入分别留证 |
| 判得准确 | judge 检查适用的状态、意图、条件、行列、值、单位等；实际自检正确／合法等价输入和针对性错误注入，应收与应拒都符合规则。解释另核，未自检不能写已验证 |
| 可复现 | 用例 ID、前置条件、规则／数据／测试／判定版本与入口明确，运行前固定标准；设计、自检和真实运行分别登记，能追到来源及实际证据 |

**逐项结论：** 填“符合／不符合／缺证待核／不适用”，附具体文件位置或记录 ID、缺口与影响、推荐处理及责任。不适用须有范围依据；缺证不能当通过或已证实错误。业务规则不明时给核实建议，不能让用户随意选一个 expected。

**整体结论分三层：** ①测试设计是否满足已约定范围；②测试准备是否就绪（含适用 judge 的实际自检）；③系统真实测试是否通过。仅审材料可确认设计项，judge 未自检则准备仍有缺项；未调用真实系统不能给第三层通过结论。按范围内必须项逐条判断，不用平均分掩盖关键缺口。修改标准需保留旧版和新依据，actual 不同本身不足以改答案。

**只检查已有测试时，可直接给 AI：**

> 请按工具包 AGENTS.md 和 14 的六项标准检查本项目现有测试。先读本轮范围、原始业务依据、数据版本、测试集、独立期望、判定及已有执行记录；缺什么就列出。逐项给结论、证据位置、缺口影响和处理建议，区分测试设计、准备就绪和真实系统通过。不要补造来源、actual 或自检结果，也不要为通过而改标准。本轮仅检查；在既有授权范围内可用隔离输入自检 judge，缺运行条件就列待核，不自动启动客户系统或有副作用接口。先给简短结论和需我判断的少量问题，明细写回现有测试记录，并汇报当前节点及流程下一步。

## AI 的学习依据与输出

执行 AI 先读本章、目标项目的接口与运行说明、原始业务依据、数据字典与快照，再读既有测试／失败。示例只教方法。通用模型的编程知识不等于知道客户口径，也不等于已读取当前资料。

先交简短的“规则来源→测试场景→预期取得办法→比较项”对应表。业务已明确的部分直接推进；关键缺口说明影响并给处理建议，不让用户猜事实。

成果包括：测试集、独立核算明细／必要脚本、判定程序、自检报告、实际问数与差异记录、解释核查和回归结论。前三项生成不等于后三项已验证。

| 名称 | 内容与来源 | 不能混淆 |
| --- | --- | --- |
| 测试集 | 多条稳定 ID、问题、前置条件、expected 及来源 | 多种同义问法不等于覆盖更多业务规则 |
| expected | 每条用例运行前独立确定的完整期望；成功时含意图、条件、行列、值和单位等 | 数字只是其中一部分；澄清／不支持的预期也有效，但须有行为依据 |
| expected_source | 定义、原始数据版本、计入／排除明细、计算步骤与来源位置 | 与 expected 关联保存，不只写“AI 算的” |
| actual | 真实执行的状态、意图、条件、查询、行列、解释与版本／trace | 示范答案、独立核算结果不能冒充实际问数 |
| judge | 按已定规则比较 expected 与 actual，输出差异和结论 | 生成该程序可用 AI；结构／数值判定运行时应确定性执行，不另查库或让 LLM 猜对错 |

以上是概念约定，落盘字段和状态名以项目适配约定为准。采用类似 `ok/clarify/unsupported/error` 的接口时，未执行是测试记录状态，不伪造成 Agent 返回的 error。文本解释按语义另核，可由 AI 协助列证据，关键争议由人复核。

## 1．按规则和错误风险选择测试

每题说明一种错误实现，以及为什么该数据能使正确／错误方法产生不同结果；若结果碰巧相同，就不足以证明这条规则被实现。

| 类别 | 例子与预期方向 |
| --- | --- |
| 正常与已知零 | 明确计入；覆盖完整且没有合格记录时按约定返回零 |
| 时间／阈值边界 | 端点两侧、跨月、恰好等于阈值；包含关系由业务口径决定 |
| 身份／粒度／关联 | 一对象多事件、同值不同事实、多卡／多角色、历史关系；不能重复放大 |
| 空值／缺数／异常 | 未定义比率、缺字段、覆盖外、缺关键记录，不能统一补零 |
| 意图与逆向 | 歧义、错误前提、不支持指标／条件；该澄清时不乱猜，该答时不一律拒绝 |
| 分组与单位 | 多指标、漏组／多组／重复组、分与元、比率与百分数、角色不同的维度 |
| 同义表达 | 保持意图与条件不变的不同问法；语义变化应另建用例 |
| 解释与权限 | 回答忠于实际范围、不编原因；有真实鉴权接口时单独测权限，拒答文字不证明后台隔离 |

场景数量按任务和风险确定。合成数据可补边界，必须说明构造规则及用途，不作客户事实；实际规模／性能验证另用对应数据和环境。安全、权限、操作测试不能擅自调用有副作用接口。

### 从规则选题，而不是先凑问题数量

让 AI 对每条关键规则依次回答：**依据是什么 → 哪种错误最值得抓 → 什么输入能让错误暴露 → 正确结果是什么 → 怎么比较 → 还没覆盖什么。** 将结果填入模板的覆盖表，再转成实际用例；数量由这些判断得出，不以“生成 100 题”代替覆盖设计。

先从正常情形固定基线，再围绕同一条规则改变一个关键条件；组合测试也需保留单条件样例帮助定位。边界检查需按有源规则考虑开始端、结束端、恰好相等及两侧，不能只测过一个月末就说时间规则全覆盖。缺数据时说明需要什么样本，按项目约定取得真实记录或另造标明的合成夹具，不替换规定使用的原始／规模数据集。

| 检查层 | 改什么 | 能支持的结论 |
| --- | --- | --- |
| 输入与理解 | 同意图换问法，或另测歧义、错误前提、不支持条件 | 对所测问法／边界的理解是否正确 |
| 数据与业务计算 | 计入／排除、边界值、重复事件、组合条件、缺记录 | 指标实现能否区分对应业务事实 |
| 判定程序 | 在结果副本中故意改时间、单位、值或行列 | judge 是否抓到指定错误；不证明 Agent 实际不会犯错 |

三层分别登记。负例不仅是“不合法请求”：条件不成立但数据完整时，正确结果也可能是正常返回零。歧义、无覆盖、未知和执行失败不能统一按零或拒绝处理，须依据本项目行为约定。

**区分力与诊断力分开：** 一题能让正确算法与错误算法产生不同结果，就有针对该错误的区分力；不同错误却可能得到相同错误总数，仍需最小反例或运行明细帮助定位。不能用一个差异直接断定原因，也不能因每题都 passed 就宣布没列出的规则也覆盖。

**给 AI 的选题话术：**

> 先按原始规则建立覆盖表，每项写来源、要抓的错误、具有区分力的数据和问题、独立期望及未覆盖项。分别覆盖问题理解、业务计算和 judge 自检，不把同义改写当新增业务规则。优先给我一组能串起完整任务的代表例，含正常、边界、条件不成立及未知；有依据的继续生成，缺行为规则的列待核。输出具体计入／排除理由和比较项，再按项目接口形成测试集；不要先凑固定题数。

## 2．独立取得并固定 expected

从已核规则和原始快照逐记录核算，或让 AI 写独立审核脚本。先用有区分力的小表校准，再扩大。审核脚本不导入待测库、不调用其生成 SQL，不用 actual 回填期望。同一 AI 可以辅助两边，但换 AI／换语言／另写 SQL 都不自动保证独立；小样本明细和来源复核用于发现共同误解。

每条记录问题、数据与定义版本、指标／日期／分组／筛选、纳入和排除的实例、计算过程、行列和单位；比率保留分子分母，浮点容差预先确定，整数计数／最小货币单位通常精确比较。未知处理无依据时列待核，不能把自己偏好的行为填成标准。

执行前固定本批测试集和核算依据。被测 Agent 只拿正常问题与应有业务知识，不接收答案表。后来有新依据可修标准，但保留旧版、原因与影响；看到实际结果不同不足以改标准。

## 3．让 AI 实现项目专用 judge

从实际接口出发，定义输入 expected／actual 和输出 passed／differences（或项目等价形式）。复用已有实现并检查，不默认重写。推荐比较顺序：

1. 状态及明确锁定的版本；失败／非成功状态按该状态契约检查，不拿残留数字冒充成功。
2. 指标、时间、分组和筛选；只可规范化已确认等价的顺序，不可删额外条件。
3. 单位、列名／列数、每行结构，拒绝缺列、重复列和非法类型。
4. 按维度键对齐行，核漏组、多组和重复组；不能用字典覆盖重复行后比较。
5. 数值、null 与零；整数精确、浮点按预定精度；布尔值、NaN、缺值不自动当数字。

差异应有字段路径／分组键、期望、实际与比较规则；通过标记必须与差异一致。SQL 可有等价写法，不要求文本相同。判定程序也不负责重新计算业务期望，独立审核程序与 judge 分开。

**必须实际自检：** 正确输入及合法行／列顺序变化应通过；分别注入错状态、错时间、错指标、额外筛选、错单位、错数值、漏组／多组／重复组、null→0、锁定版本错误等，应报告相应差异。按已支持功能选择并补齐，不凑固定数量。只作自身相等比较不能证明能抓错。合成注入与 Agent 真实错误分开保存。

## 4．使用项目工具运行并留证

接入既有测试运行器：读取用例→调用真实 Agent／查询入口→捕获 actual→调用 judge→保存报告。已有框架时复用；没有框架时 AI 按已核接口编写最小适配，不能假称本包已内置执行器。

记录问题、数据／库／Skill／判定版本、实际加载实例、环境、开始结束与状态、实际输入输出和 trace 位置。运行目录按版本新建；未执行／中断不写通过。报告跑完和全部通过分别核对，来源若未被复制到报告，须保留原测试集链接。

结构比较通过后核解释：客户、期间、实际筛选／分组、指标口径、单位／空值、限制均忠于证据；相关性不直接当因果，系统可计算不等于业务效果。未经实际验证的范围明确列出。

## 5．按证据追查，不靠猜测修改

先固定失败及版本，由报告 differences 找到单次 trace。工具名和文件名依适配表，不假设所有系统都有课程 trace 文件。

| 观察到的问题 | 去读什么证据 | 可能的修复层 |
| --- | --- | --- |
| 意图／条件不对 | 原问题、实际理解输入输出、目录与可用维度 | 目录／输入、意图程序或需澄清的真实歧义 |
| 规则似乎被误解 | 构建实际输入、原件、模型、采用记录 | 业务模型／口径依据，必要时取证 |
| 计算不对 | 实际加载定义、派生处理、生成查询、原始数据明细 | 加载旧版、转换方法、数据或引擎实现 |
| 值对但解释错 | 实际结果、解释输入／回复 | 解释环节及目录说明 |
| 标准或比较可能错 | expected_source、审核脚本、judge 与注入记录 | 有依据地修标准或比较方法 |

输出“现象→已证实证据→待验证假设→推荐处理→影响依赖→验证办法”。同一总数差异可能有不同原因，不由数字直接定责。没有证据时列缺口，不反复随机改提示词直到偶然通过。

## 6．修复、回归与验收

修业务输入或构建方法后，重新生成受影响库、检查和加载；修 judge 后重做正反例。开发中局部复跑帮助定位，收尾默认回归全部已纳入本轮基线的用例，包含原正确例、状态、分组、同义问法及已纳入规模集。项目另有基于风险的回归约定时写清范围、理由和剩余风险，不把未跑写通过。

若共享定义、引擎或判定变动，分析所有依赖方；期望是否仍有效按业务依据判定，不能为了通过而改标准。重新比较旧 actual 只证明判定变化，不是新问数。验收按 [15](15-验收与ETL交接.md)逐项判断。

## 可直接交给 AI 的指令

> 按本包 13 的项目适配和本章实现或完善测试集、独立期望与 judge。你先读资料并给规则覆盖及缺口摘要，再推进已明确部分。用固定原始数据独立核算，保存 expected_source 与明细，不能复制 actual 或待测 SQL。实现完整结构比较并实际执行正反例自检；复用项目运行器完成真实测试和解释核查。保留原失败，按证据定位、修复、回归。交付测试、核算依据／脚本、判定、自检及运行报告；给当前节点、完成／失败／未执行项和流程下一步。需业务判断时给我证据、推荐处理和选择，不要求我先手写全部用例。
