# E2 从候选到模型：对象、身份、关系与时间

前置：K3–K6、K8。核心问题是“怎样组织才支持本任务”，不能只把原文分类成几个标题。例子均为教学假设。

## 先用任务问题检查表达能力

列出本模型应该回答的问题，以及相似但不能混淆的情况。例如“谁提交了申请”和“谁实际处理”是否相同；“现在归谁负责”和“发生当时归谁负责”是否相同。问题来自本项目任务，不规定固定数量。

这些问题用来选模型结构；测试的正确答案仍须从独立原始依据取得，不能由选好的结构反推事实。

## 选择对象的判断顺序

| 遇到的情况 | 考虑怎样表达 | 怎样检验 |
| --- | --- | --- |
| 只描述一个对象的特征 | 属性，例如本次任务只需展示的备注 | 是否需要独立身份、生命周期或关联；不需要就别扩大模型 |
| 独立存在且需要跟踪 | 对象，例如设备、机构、合同 | 能否说明它是什么、怎样认同一对象、为何与任务有关 |
| 同一组参与者之间重复发生 | 独立事件或带属性的关系，例如一次维修 | 能否区分每次的时间、状态、输入和结果 |
| 同一个实体承担不同职责 | 同一对象加不同关系角色 | 申请者、处理者、接收者能否分别表达，而不重复造“人” |
| 类型有不同规则 | 必要的分类／子类型及适用条件 | 规则真有差异吗？不要按每个标签或实例建子类型 |

没有唯一固定画法。写出所选方案为何足够支持任务、放弃的简化为何会丢信息；不为形式完整列无关对象。

## 身份与名称怎样处理

类型是“维修事件”，实例是某次具体维修。对象的业务身份与数据里的编号可能不同，需要核实映射。

同名不自动合并，改名不自动产生新对象；一个编号换系统后是否仍指同一对象要有依据。历史属性不能被当前值替代。材料缺身份判断规则时保留未知，不能用代码临时拼接的键冒充客户业务定义。

## 每条关系要检查的内容

写出两端对象、关系含义与角色、方向、允许数量与是否可以暂缺、有效时间、来源及例外。例如“一个人可多次提交申请”不等于“每次申请可以有多个申请人”；两个方向的数量分别判断。

“最多一个”不等于“必须有一个”；“样本里没出现多个”不等于制度禁止多个。关系数量未知时写未知，而不是默认一对一。

若关系自身有日期、状态或可重复发生，考虑让它成为独立事件。不要把两次事件的属性拼在一起满足一条规则，也不要用今天的关系回答历史归属。

## 粒度和时间怎么落到文字

分别说明业务对象是什么、每条源记录是什么。一次业务事件可能在多张表或多条日志里出现；一张表也可能混有多个业务阶段。对象与表不需要一一对应。

区分事件发生时间、记录时间、规则生效时间、查询判定时间。只采用本任务需要且有依据的时间表达；是否包含起止日、跨日时区、规则变更如何影响历史等，没有资料就保留待核。

模型可描述状态和状态变化，但不要凭空补出完整状态机。客户只说明“已提交、已完成”，并不能自动推出所有中间状态和允许跳转。

## 用实例检查模型，而非只看图好不好看

选本项目适用的同名、重复事件、多人协作、缺失关系、历史变化或例外。沿问题检查对象身份、关系、规则和答案如何连接。若必须靠模型中未说明的常识才能解释，就补依据或保留限制。

图只作辅助：关系角色和规则含义须有文字，让人和 AI 不依赖视觉猜测。自然语言和小表格足够时不必引入专门建模语言。

## 学完要能做到什么

说明本项目一个关键对象为何独立建模，一条关系两端分别是谁，拿一个易混实例证明这种表达有用，并列出尚无依据的身份或数量约束。记入实施方案的“建模重点”和模型的“建模选择”。
