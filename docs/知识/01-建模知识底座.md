# 建模知识底座：人和 AI 先理解这些

本章给出本包使用的概念与判断方法。内容是依据课程方法的通用整理；例子均为教学假设，不是行业通则。来源索引见 [SOURCES](../维护/SOURCES.md)。

本章先建立完整认识；需要生成实施方案或执行建模时，再按 [08 学习路线](../建模/08-实施方案与学习路线.md)补读知识卡：[E1 材料与证据](材料提取与证据判断.md)、[E2 对象关系与时间](对象关系与时间建模.md)、[E3 规则流程与边界](规则流程与边界.md)、[E4 接入与效果判读](知识接入与效果判读.md)。每张卡都有判断方法、易错例和针对本项目的学习产出。

## K1 我们在做什么

这里的业务模型，是围绕一个任务，对客户的业务对象、属性、关系、规则和工作方式作出的有依据、可维护的说明，同时保留范围、建模理由及未知。

它让人和 AI 能理解“客户说的是什么、怎样判断、哪些事情不能下结论”。输出可以是自然语言、小表格或带文字说明的图，不要求图数据库或专门建模软件。

**模型内容比访谈摘要多一层组织判断：** 摘要保留说过什么；模型还要解释为何区分这些东西、怎样关联、哪些条件共同决定结果。AI 辅助这层组织，FDE 检查其依据与用途，相关业务角色核实业务含义。

使用：先说清谁的哪项工作需要模型帮助，再决定建哪些内容。记牢目的；定义不必逐字背。

## K2 模型与周边材料怎样分工

| 材料 | 解决什么问题 | 容易混淆的地方 |
| --- | --- | --- |
| 项目背景 | 我们为什么做、给谁用、本轮范围和产物是什么 | 不能把希望达到的效果写成已经发生 |
| 业务模型 | 对象是什么意思、怎样关联、按什么条件工作和判断 | 不是只列指标含义，也不是数据库设计 |
| 业务模式介绍 | 企业提供什么、服务谁、怎样经营 | 是背景的一部分，不能替代细化到任务的规则和关系 |
| 原始材料与核查记录 | 依据是什么、怎样取舍、什么仍待核 | 原文可被引用，不必整段复制进模型 |
| 指标口径 | 具体数什么、怎么算、时间与范围是什么 | 业务对象相同，报表口径仍可能不同 |
| 数据字典与剖析 | 实际字段、一行代表什么、数据覆盖和质量怎样 | 字段名像业务名，不证明含义一致 |
| 语义模型与派生数据 | 怎样把定义映射为工具可计算的数据结构与规则 | 是实现层，不能替代业务依据；具体形式依技术栈 |
| ETL 规则 | 怎样整理、转换和核对数据 | 含义不明确时不能仅凭程序方便决定业务规则 |
| SOW 与交付记录 | 交付范围、成本、时间、验收和变更 | 可以引用业务范围，项目管理内容另存 |

使用：收到新问题先判断属于哪层，再改相应成果。记住业务含义、计算定义、数据、实现和交付分别承担什么。

## K3 从任务决定模型的大小

先写一个可核查的任务：谁提出什么问题／使用哪些材料／需要得到什么答案或决定／范围到哪里／不包含什么。

例如“说明某天一台器材为什么被占用”需要器材、一次借用、借用者、起止条件；若本轮不做采购预算，就不必扩展出采购审批全流程。

够用标准是模型能区分本轮关键情况，且能指出证据与限制；不是把企业所有事情收集完。先有局部带未知版本，再随任务扩展。

## K4 对象、类型、实例：什么值得单独建

- **类型**：一类有共同含义的事物，如“器材”“借用记录”。
- **实例**：某一台器材、某一次借用。
- **对象选择**：需要独立识别、反复发生、跨时间跟踪，或承载自己的属性与关系时，考虑单独建对象。

例：同一人两次借同一器材。若只写“人—借用—器材”，两次时间和归还状态可能混在一起；把“每次借用”建成独立对象，可以分别说明起止和状态。

反例：展示用颜色若只用于一句说明，未必需要独立“颜色对象”。不能见名词就建对象，也不必把每个字段建成类型。

操作：列候选对象，说明它帮助回答哪一问题；用同名、重复发生或历史变化的例子检验。不由样本中只有一条记录推断永远一对一。

## K5 属性与关系：分别表达什么

**属性**描述对象特征，如借出日期。**关系**把具有业务含义的对象联系起来，如一次借用涉及哪台器材、由谁借用。

每条关键关系说明：两端是谁、角色是什么、可一对几、何时成立、依据是什么。未知就标未知。

例：“申请人”和“实际领用人”可能指同一人，也可能不同。不能因为两个字段暂时相同就合并角色。数据库把某个关联存成字符串，不改变其业务关系含义。

操作：把“谁和谁怎么联系”写成业务句，再拿实例核对，最后才讨论技术映射。必须会区分角色，具体字段随用随查。

## K6 身份、粒度与时间：防止把不同的事混成一件

**身份**决定是不是同一对象；名称不一定唯一。**粒度**说明一份记录代表什么，比如一次借用，而不是一个人。**时间**说明规则或状态在哪段时间成立。

例：两次借用不能用“借用者＋器材名称”直接合并；历史占用不能只看器材今天的状态。

操作：对象问“怎样认同一件”，记录问“一条是什么”，规则问“何时有效”。缺识别依据或历史资料时保留限制；不要猜关联键、默认去重或补出历史状态。记牢这三个问题。

## K7 规则、流程与候选动作

**规则**写清：作用对象、触发或条件、判断结果、适用时间／范围、例外和依据。

**流程**写清：什么触发、谁做什么、输入输出、交给谁、怎样结束。客户实际工作流程是模型内容；FDE 调试或交付排期另记。

**候选动作**表示想做什么，另写所需条件与权限。客户觉得“自动提醒不错”，只支持方案接受度，不能证明系统已经能提醒或被授权发送。

例：教学材料如果明确“归还日不计占用”，模型必须保留日期边界。不要套用此例给其他客户；先取该客户自己的依据。

操作：规则尽量能拿正反例判断，流程能沿一件实际工作走通，候选与已经执行分别说明。记住条件、时间、权限不能省。

## K8 证据与建模选择：AI 必须分清

| 内容性质 | 记录方法 | 不能做什么 |
| --- | --- | --- |
| 原始陈述／记录观察 | 谁、何时、原文位置、范围；观察到什么 | 不能自动上升为适用于全公司的制度 |
| 目标、偏好或观点 | 保留提出者和原措辞 | 不能当成实际效果、根因或授权 |
| FDE 建模选择 | 采用什么表达、为什么有助任务、依据和其他方案 | 不能伪装成客户原话 |
| 候选假设 | 标待核，说明影响和需要的证据 | 不能靠 AI 置信分升级为事实 |
| 实际确认 | 记录确认者、具体事项、版本、适用范围 | 一句认可不能扩展到未讨论事项 |

例：“把每次借用建成独立对象”可以是 FDE 的建模选择；“同一人可以多次借同一台器材”则须有材料依据。建模选择可由 FDE 说明理由，不要求业务方先懂对象术语。

使用：候选回查来源是否支持整句话，同时从任务和原件反查遗漏。只摘一句回答、丢掉前面的问题，可能把提问者的假设错记成客户确认。

## K9 未知、分歧、变化与不适用

- **未知**：没有足够依据，写缺什么、影响什么、向谁或哪份材料核实。
- **分歧**：已有说法可能不一致，先比时间、范围、含义。互补说法和共同不知道不必强行算冲突。
- **变化**：新旧规则可能适用于不同时间，不能只因文件更新就覆盖历史。
- **不适用**：与本轮任务无关，写理由；有需要却拿不到资料属于未知。

例：外借政策未提供，合理输出是政策未知，不是“公司禁止外借”。已有正常借用范围内的规则仍可使用，不必所有问题一律拒答。

## K10 从材料到模型不是一次总结

1. 盘点任务、来源和缺口。
2. 提取带上下文和范围的候选认识。
3. 双向核查，记录采用、改写或暂不采用的理由。
4. 选择对象、身份、关系、规则和时间表达，解释其对任务的作用。
5. 用正常、例外、未知和越界场景检查，再验证 Agent 实际使用。
6. 随新证据修订受影响部分，保留差异和回归证据。

AI 可辅助所有整理环节，但不能替客户创造事实、替本人登记未作出的判断。模型正文宜清楚简洁，过程与运行记录另存引用。

## K11 什么叫“正确而且有用”

分三层：**认识有依据 → 表达支持任务 → 实际使用正确**。

第一层查原文与条件；第二层用具体实例检验关系、时间和规则能否区分；第三层检查实际请求是否包含正确模型，以及回答是否用对。只做第一层不能证明 Agent 效果；只看一个正确回答也不能证明整体模型可靠。

测试期望须回到原始资料和独立核算，不拿生成的模型或回答自证。检查必须包含的事实、不能违反的约束、应该承认的未知；程序结构检查与人的含义审阅各有作用。

记牢三层，其余执行方法查 [06](../建模/06-检查测试与版本.md)。

## K12 业务模型怎样接指标与数据工作

业务模型提供对象、身份、关系、规则、适用范围；指标定义进一步决定数谁、时间窗口、筛选、聚合和单位；数据映射核对实际字段和粒度；具体工具再实现可计算定义。

业务模型不是整个指标库的替代品。数据剖析发现新取值时，先判断是记录格式问题还是业务含义变化；后者要回到材料和模型核查。

用 [07](../建模/07-指标库衔接.md)交接输入，再按 [13](../指标库/13-指标库建立手册.md)建立指标库、[14](../指标库/14-测试判定与证据排查.md)测试、[15](../指标库/15-验收与ETL交接.md)验收并交接 ETL；不要因为模型建立完成，就宣称指标已构建或查数已验证。
