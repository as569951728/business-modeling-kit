# 业务模型测试方法论：让 AI 出题、独立判读和回归

**用途：** 把业务任务、原始证据和待测模型变成有依据、能发现错误、可以复验的测试。AI 负责整理与起草，FDE 核关键业务判断。设计完成、真实验证、模型采用及客户验收分别记录。

先看[维修测试示范](../../examples/设备维修-业务模型测试示范.md)，再让 AI 按本章与[测试模板](../../templates/业务模型测试.md)处理自己的材料。已有同等台账直接复用，不要求人再填一套表。

本章依据 W02 的模型使用验证、W03 V07 的独立校验原则，由导师综合为通用方法；六步流程及 BT 编号不是老师新增必交项。来源与迁移边界见[来源说明](../维护/SOURCES.md)。

## 目标、材料和完成条件

目标是检查三个问题：**原话有没有理解错？模型能否支持本次业务任务？实际 Agent 是否正确使用了模型？** 文档齐全、回答流畅或 AI 自评正确都不足以证明这些目标。

你只需提供当前任务、资料和已有模型的位置，AI 自己盘点下表。尚无模型时也可从任务和原件准备测试候选。

| 材料 | 作用 | 缺失时的处理 |
| --- | --- | --- |
| 本轮目标、使用者、场景、范围 | 确定必须支持和暂不支持什么 | AI 整理已有约定，只列影响标准的待核 |
| 原始访谈、制度、材料与实际确认记录 | 独立确定事实、条件、来源权限和未知 | 只有模型自述时，不能认证其内容正确；可先查内部一致性、列取证缺口 |
| 采用模型、候选取舍及方法版本 | 确定被测对象，追查不当归纳 | 草稿和已采用分开，不虚构本人或业务方确认 |
| 实际案例／记录及覆盖范围 | 让正确和错误理解产生不同结果 | 可以另造标明用途的合成测试材料，不当客户事实 |
| 既有测试、失败和变更记录 | 复用已核标准、保留原正确案例 | 没有则先围绕关键任务设计，不凑题 |
| 实际 Agent 入口、输入输出约定与日志 | 取得真实请求、加载证据和回答 | 设计可继续，使用验证保持未运行 |

**测试准备完成：** 关键规则有覆盖或明确缺口；期望可回溯；正误可以区分；关键标准按项目已有约定核定；运行前固定本轮版本。

**实际验证完成：** 有真实输入、加载／检索内容、回答和逐项判读；处理或明确保留失败、未覆盖与待核项。通过结论限定所测版本、任务、样本和环境，不能保证所有未来场景。

## 分清三层测试

| 层次 | 检查 | 证据 |
| --- | --- | --- |
| 提取与来源忠实 | 有没有漏条件、否定、时间、分歧或错认说话人 | 原件→候选查漏，候选→原件查支持 |
| 模型内容与任务支持 | 身份、关系、规则、流程、范围和未知能否区分关键实例 | 独立规则台账、模型条目、取舍与实例检验 |
| 实际使用 | 指定模型是否进入实际请求，回答是否正确应用 | 实际请求／检索片段、完整回答、独立期望及判读 |

不同文字、表格或对象组织方式可以表达同一业务含义。除非项目已有格式契约，不能强制模型逐字等于示范，或必须使用某个对象名。

录音／沟通提取先用 [10 的 EX01–EX08](../访谈/10-沟通记录到业务信息.md)；只准备访谈则用 [09 的 QC01–QC10](../访谈/09-访谈准备与交接.md)及[访谈准备模板](../../templates/访谈准备.md)。问答测试不替代这些检查，只核文字不等于回听准确，忠实提取不等于说法已获核实。

## 六步工作法

```mermaid
flowchart LR
    A[任务和原始依据] --> B[1 定范围与规则]
    B --> C[2 设计能抓错的案例]
    A --> D[3 独立期望与判据]
    C --> D
    D --> E[4 审核测试集并定版]
    E --> F[5 实际运行与判读]
    F --> G[6 定位 修订 回归]
    G --> B
```

这六步是测试内部方法，服务于建模流程 S4 测试准备、S5 实际使用、S6 修订回归，不新增项目阶段。S1–S3 有明确任务和依据时即可提前准备候选，无需等模型全部写完。

### 1．从任务和原件建立规则台账

AI 先写“谁在什么场景完成什么任务，错误会影响什么，本轮测哪一层”，再整理：关键认识／适用条件／原文位置与性质／已核或待核／对应模型位置。

**双向查：** 原件和任务里的重要内容，模型有没有遗漏；模型写出的重要结论，原件是否支持。测试设计 AI 可以读模型确定检查对象，但不能抄模型作正确答案。

个人做法不自动上升为制度；提问里的假设不算对方确认；资料未提供不等于现实中不存在。角色或适用范围不清时列待核，不能用行业常识补成客户规则。

产物是规则与覆盖表，优先覆盖会改变任务结果或造成越界的认识，不把所有名词都机械变成题目。

### 2．按“想抓什么错”设计实例

对每个关键目标问：正常应怎样？最可能怎样理解错？改掉或去掉哪个条件才会暴露错误？先用最小而清楚的例子，再覆盖重要条件组合，不无限组合。

| 方向 | 怎样设计 | 要防的错误 |
| --- | --- | --- |
| 正常任务 | 给足正常需要的材料，完成真实工作 | 一律不知道也能过关 |
| 身份、关系、重复事件 | 同名不同对象、同对象多事件、不同关系角色，按适用性选 | 合并不同工单、后次覆盖前次、错配人员 |
| 条件、时间、例外 | 正常成立、条件不满足、边界两侧及已知例外 | 漏限定、误用当前状态；日期端点依据本项目规则 |
| 未知和分歧 | 缺关键材料、不同适用范围或确实冲突 | 编默认值、把未知当否定、擅自裁决 |
| 错误前提与任务边界 | 问题暗含错误事实，或要求超出当前能力 | 顺着问题承认错误结论、宣称未发生的动作 |
| 换问法与多场景 | 同意图换说法；共享定义用于不同场景、角色 | 只会固定措辞、把 A 场景规则误用于 B 场景 |

没有相关规则就说明不适用，不能为了覆盖虚构制度。没有实际权限配置时，只能测回答边界，不能据此证明登录、接口授权或后台隔离安全。

**每题必须写出一种具体错误做法，并说明这个输入为什么能使它暴露。** 若正确和错误做法在该样本上结果相同，就不能用它证明该规则有效。同义问法不重复计算业务规则覆盖。

先测会造成关键结论错误、无依据断言、越界或影响多个下游的情况，再补低影响表达。优先级由业务后果与依赖决定，FDE 核实际影响；数量由范围决定，不固定“必须十题”。

### 3．独立写 expected 和判据

运行前，从原件、确认记录和案例推导四类要求：

1. **必须说对的事实：** 对象、事件、关联、状态或完整集合。
2. **必须保留的条件：** 场景、角色、日期、来源范围。
3. **不能断言的内容：** 原件不支持或明确否定的结论。
4. **未知的处理：** 保留什么未知、需补什么；同时回答已有依据支持的部分。

每题附来源定位和推导，不只写“根据业务模型”或“由 AI 判断”。有数量时核范围、粒度、单位、明细和完整结果，不仅比总数。

独立指依据和推导独立。同一 AI 可辅助，但须回查原件；换 AI、换会话、另写 SQL 不自动独立。不能从待测结果反推 expected，也不能只用待测模型自证。

没有确定业务答案时，可以检查是否保留未知；若连应如何处理都没有依据，则该项待核／不可判，不能偷偷把“澄清”设成所有未知的标准答案。

| 输出 | 判定办法 | 注意 |
| --- | --- | --- |
| 有约定的结构字段、集合、数值 | 程序按身份、字段及条件比较 | 容差、顺序、空值须事先约定；不只看总数 |
| 自由文本 | 按上述四类要求逐项核语义，引用 actual 原句与原件 | 合理改写可通过，关键词或另一 AI 自评分不够 |
| 混合回答 | 结构与解释分别检查，再判整题 | 数值正确但解释越界不能整题通过 |

AI 可辅助文本判读，须展示标准、实际语句和理由；关键结论、争议和证据不足交 FDE／适当业务人员复核。W03 查数 judge 的“不调 LLM、不另查数”是该工程运行契约，不能推广为所有问答必须采用相同 JSON 协议或逐字匹配。

### 4．审核测试集，也检查判定方法

先由 AI 自查，再交 FDE 简短审核摘要。重点是期望依据、正常与边界覆盖、未知有没有被偷换成事实、题目能否抓错。已有确认直接沿用，不重复逐题审批。

另存**正确和错误示范回答**检查判据：正确改写应通过，漏事件、错配身份、把完工当验收应被具体标准拒绝。若有判定程序，实际运行这些正反例；只写示范不记程序自检通过。判据自检和真实 Agent 测试分别记录，不把注入的错误冒充 Agent 曾犯错。

| 编号 | 质量要求 | 反例 |
| --- | --- | --- |
| BT01 | 测试范围对应实际任务 | 只考术语，没测解释工单 |
| BT02 | 原件查漏与模型查支持双向进行 | 只从模型抽题，模型遗漏也一起漏掉 |
| BT03 | 期望有独立依据和适用范围 | 模型这么写，所以就对 |
| BT04 | 输入能暴露具体错误 | 只给一次派工就声称证明不会覆盖历史 |
| BT05 | 正常、相关边界与未知兼顾 | 一律拒答也通过 |
| BT06 | 问题、输入、期望含义一致 | 换了意图仍沿用同义题答案 |
| BT07 | 判据识别合理答案与关键错误 | 出现“验收”二字就通过 |
| BT08 | 正常输入与答案分离 | 问题中先列出期望结论 |
| BT09 | 版本、依据状态和运行结果分开 | 文件生成即登记通过 |
| BT10 | 缺口、排除范围与责任明确 | 无环境却宣称权限测试完成 |

用户不懂定义时，AI 给“白话说明—来源与未知—推荐处理—理由与影响—其他选择”，允许选择或自由回复。缺证据就推荐找谁补什么，不能让用户猜事实。批量同意绑定版本和条目，不扩大到待核或新增内容。

定版绑定测试、期望及来源、数据、待测模型和方法；以后可凭证据修订，但保留原因和影响。不存在“必须研发前准备齐全部测试”的统一要求。

### 5．实际运行，判断模型有没有起作用

进入已授权的执行任务后复用现有环境。缺环境仍可完成设计，actual／judge 写未运行；本包不内置 Agent 或测试执行器。

- 验证侧持有原件、expected 与判据；被测 Agent 只接收正常输入、应使用的知识和授权工具内容，不接收判分表或示范答案。
- 保存实际请求、加载／检索到的内容、完整回答及失败日志。文件存在或 AI 自称读过不是本次加载证据。
- 先看加模型后的绝对正确性，再按需做有／无模型对照；W02 实操按任务书保留此对照。
- 对照固定底层模型、问题、案例事实、工具和尽量一致的设置，两组各用干净上下文，只改变业务模型输入。无模型组可以答对，有模型组也会变差，如实报告。
- 波动影响结论时，事先约定重复办法并保留所有尝试，不只挑最好一次。题目用于调优后，可补未参与调优的代表案例，避免只记住测试题。

逐题记录 expected／actual／judge：通过、失败、证据不足或未运行，给出满足／违反项。材料明确却答不知道属于未完成；证据不足用于评价本身无法可靠进行，不能掩盖已知错误。

汇总关键规则、场景和未覆盖，不只给总通过率。重要错误不能被简单题稀释；采用与交付按既有约定，没有约定就报告事实和限制，不自设“90% 即验收”。

### 6．定位、影响分析和回归

先固定失败时的输入、原件、模型、期望、回答和判读，也检查测试本身可能错。

| 证据表现 | 优先检查 |
| --- | --- |
| 期望与原件不符 | 核来源、条件、推导；凭证据改期望，不迁就 actual |
| 原件明确，候选或模型漏／错 | 查输入、提取方法和核查取舍；改方法后重生成受影响产物，再核查 |
| 模型正确，但实际请求没带入 | 查加载、版本或检索，不用扩写模型掩盖接入问题 |
| 模型已正确带入，回答仍错 | 查问题理解、上下文、生成约束、执行模型或工具结果 |
| 回答正确但被判错 | 修判定，再做正反例自检，保留纠正依据 |

沿 **原件→候选／取舍→模型条目→测试／使用任务→下游指标或实现** 找影响范围。只重建受影响产物；依赖不清、共用规则或方法变化较大时扩大。不能盲目全重建，也不能只手改一次输出就宣称方法已修好。

先复跑原失败、关联边界和原正确代表题；重要采用／交付前按约定完整测试集回归。未全量就说明已测、未测和原因；全量通过也只证明该集合范围内未发现问题。新证据改变业务规则时可修订 expected，保留原标准、失败及变更理由。

## 可直接交给 AI 的指令

```text
请按工具包 AGENTS.md 和 docs/建模/06-检查测试与版本.md，为当前业务模型设计测试。
读取当前任务、原件索引、模型、取舍、已有测试和进度；从对话与工作区取得位置，不要求我先分类或填表。
本轮交付测试设计；如本次另有明确执行授权，则按授权范围衔接实际验证，否则 actual／judge 保持未运行。

1. 说明任务、范围和测试层次，列已读材料、版本和影响判断的缺口。
2. 从原件建规则与覆盖表，双向检查模型遗漏和无依据断言；保留来源性质、条件和未知。
3. 按“要抓什么错误→什么输入能暴露它”出题，覆盖正常及适用的身份关系、条件时间、例外、未知分歧、错误前提、边界与多场景。同义问法不重复算业务覆盖。
4. 逐题给来源与推导、必须说对、必须保留、不得断言、未知处理和判定方法。禁止抄待测模型／结果作答案。合成材料另标，不当客户事实。
5. 按 BT01–BT10 自查，用正确和错误示范回答检查判据；示范不填 actual，不冒充 Agent 失败或程序自检。
6. 集中给真正需要我判断的事项：白话解释、依据、推荐处理、理由和影响，允许我选择或自由回复；已有确认不重复问，缺证据不让我猜事实。
7. 复用已有台账，必要时按 templates/业务模型测试.md 保存覆盖、用例、判据、自查、待核与版本。先展示一条完整用例，其余给简明索引。
8. 若已授权实际执行，分离业务输入与期望，保存真实加载、请求和回答，逐项判读；按项目要求公平对照。失败核测试自身及输入、方法、模型、加载、回答，沿依赖决定修订与回归范围。

结束说明当前节点、已完成、尚缺／需谁处理、流程下一步。设计完成不登记使用验证通过，额外建议不替代既定下一步。
```

## 人与 AI 的分工及记忆要求

用例和实际结果准备好后，按 [12 验收与完成判定](12-业务模型验收与完成判定.md)汇总范围、版本、证据、关键失败和复核，分别形成内容与使用结论。测试报告是验收依据的一部分，不能自动替代采用、客户签收或全部业务正确的判断。

AI 整理材料、设计覆盖、起草用例、做自查、执行已授权检查并汇总；你核关键规则、期望、缺口与失败处置，业务方核其职责内的事实和验收要求。不必手写全部题目，也不把另一 AI 的“通过”直接当业务正确。

记住：**从任务出发，从原件定标准，用正反例证明能抓错，用真实记录证明实际效果。**

版本最少关联任务、原件快照、方法、模型、执行模型及设置、测试／期望、实际请求／回答、判读和修订回归。已有日志直接引用；没有专用工具，用清楚的文件名、日期和引用也能开始。追溯靠记录与工具共同实现，客户成果留客户项目。
