# 可视化核对与逐步反馈

使用者通过页面看当前工作、理解成果、核对与提意见；知识 Markdown、原始资料和实施记录由 AI 阅读维护。页面是同一组记录的可读呈现，不另建一套业务事实。默认仍按 [11](11-工作进度与接续.md)一步一交付，由用户指示下一步。

## 当前提供到什么程度

[交互页面样稿](../../examples/ui/review.html)使用本包虚构维修案例，演示模型／指标核对、来源展开、二次访谈问题与反馈下载。下载仓库后用浏览器打开；GitHub 的文件预览不执行此页面。

样稿尚未连接任何客户工程，也不读取项目文件、调用 AI、写回项目或自动推进。未点击记录的选择仍是临时输入；点击“记录本条核对／确认理解一致”后保存到当前浏览器，刷新可恢复。浏览器记录不是 AI 已接收或项目已归档，仍需将导出文件交给 AI，或直接在聊天里说明。清除浏览器数据、换浏览器或换地址不会共享这份本机记录。页面与同目录 review.js 一起使用。

现有样稿为业务模型／指标各两个核对点，同一模型或指标可按明确内容拆点，不冒充四个独立业务成果。使用者认可的分层阅读、宽屏布局仍保留；真实项目接入及自动写回方案未实现，没有通用 UI 生成器或独立工作台。

## AI 怎样交可核对的材料

1. **先找已有页面。** 项目已有合适的核对页／工作台就复用，保留其来源与反馈约定。没有时先按本章准备当前一步的小页面草稿，展示给用户确认阅读方式，再接真实数据或持久化；不借此开发完整平台。仅“了解项目”仍只读，不生成客户文件。
2. **保持一个权威来源。** AI 从当前项目登记、实际产物和原件形成页面；展示项目、模块／阶段、条目 ID、产物版本、来源定位及生成时间。旧快照显式标记版本，不能装成实时状态；缺项显示待核，不填示例值或假进度。
3. **只讲当前一步。** 先呈现这一步的目的、成果、判断点，给一个贴近实际的例子；默认展开少量条目，其余按批次查看。用户不必读方法库、审代码或逐条手填后台台账。
4. **反馈与采用分开。** 页面上“理解一致”“需要解释”“修改意见”“带去业务核实”都是处理意向，允许自由文本。记录原话、条目版本和时间，AI 回读后先总结处理和影响；有明确授权的本步动作直接落实，下一步按已解释范围由用户指示。不能用点选补足未知事实。
5. **可追溯地接收。** 当前样稿支持本机记录、单条／本批导出；未交回／未写入项目必须明确。实际保存、重载、版本冲突和失败都要验证，不能只改徽标就称已保存。反馈绑定的旧版本已变化时先列差异，不把旧决定静默套到新版本。接入项目后必须由真实接收结果决定是否显示“已提交”。

## 核对任务必须有明确入口

用户说“不知道在哪里核对”时，先检查任务与页面是否匹配，不能只复述概念或再次给一堆文档。每次邀请核对至少交代：**本次节点与范围、要判断什么、直达入口、页面具体位置、按哪个按钮、记录保存在哪里**。

- **材料已备好：** 交实际验证可打开的链接，定位当前项目、条目与区域，说明例如“左侧逐笔明细和计入理由 → 右侧判断”。只有主页链接不够；页面不支持深链时提供准确 tab／条目／区域名称。不要让用户猜对应关系。
- **页面尚未准备：** 明确当前下一步是 AI 准备材料，显示“待准备”，不能登记为“待用户核对”，也不能把旧页或 Markdown 目录包装成新入口。准备好后再邀请核对。
- **当前页只是旧快照：** 明确原节点、版本、用途和已有确认，不让用户在旧页面重复确认。将“下一流程节点”与“现在可核对的任务”分开。
- **M1 与 M2 不混用：** M1 的简化例子帮助理解口径；M2 的复核需要逐笔输入、计入／排除理由、事前独立期望及依据和错误算法的拦截目标。未准备成可核材料时，不因页面已有“一例看懂”就称 M2 就绪。

样稿的直达参数为 `module=metric|model`、`item=条目ID`，可加 `section=rules|example|feedback` 与 `#review`。例如在[样稿](../../examples/ui/review.html)地址后附 `?module=metric&item=MET-DEMO-01&section=example#review` 可定位指标例子；实际项目由 AI 替换为对应真实入口，不能照抄演示条目。样稿将下一步 M2／S4 标为页面待准备，不提供不存在的核对入口。

## 表单操作：记录、导航、导出分开

| 操作 | 使用者预期 | 页面必须做到 |
| --- | --- | --- |
| 选择理解一致或填写意见 | 编辑本条判断 | 不因选中单选项就算完成；未记录可见 |
| 记录本条核对 | 明确提交这次本机记录 | 主要按钮；选理解一致时写“确认理解一致”，其他处理保留原意，真实写入后显示结果及保存位置 |
| 上一条／下一条 | 浏览同批其他内容 | 不强迫同意、不自动记录；临时输入切页保留，未处理仍计未记录。最后一条进入本批汇总 |
| 下载本条／本批记录 | 带走或交回证据 | 辅助操作，不是主确认按钮；导出绑定条目、版本、原话、时间、来源及接收状态 |

“已记录几条”“理解一致几条”“待跟进几条”“未记录几条”分开。待解释、修改、业务核实不合并为已通过；看完本批不自动进入下一阶段。自由原话同样有效；修改意见须带具体说明。已经记录后又修改，明确提示未记录修改，不能把旧记录下载伪装成新意见。

保存需绑定项目／模块／条目／版本／内容快照，刷新只恢复匹配记录；损坏、旧版本或其他页面同时修改时保留原记录并提示，不静默覆盖。保存失败不增加进度，不显示成功；保留可复制原话供用户交回。样稿的本机保存仅用于验证交互，客户正式归档仍按 16 与原项目记录执行。

## 页面默认呈现什么

### 阅读层次：重点先到眼前

依据使用者对首版“没有重点、眼睛看着疼”的反馈，不能把后台记录逐段平铺到页面。默认按三层呈现：

1. **首要判断：** 顶部只突出“这次要确认什么”，用一句话概括；关键待核或限制必须可见，不能藏在折叠里。
2. **当前行动：** 用短标题、编号、分组和留白呈现。访谈按“找谁问 → 现场怎么问 → 至少带回什么”；模型／指标按“本条关键认识 → 结构化解释 → 留下判断”。现场问法与给本人的解释分开。
3. **需要时再看：** 长背景、详细影响、完整来源、后续处理默认折叠，展开能回看。减少默认文字不删证据、范围或未知。

主标题、关键结论、正文、来源元信息要有明显视觉层次；正文保持易读字号和行距、避免长行，强调色只用于重点或当前行动，不每句加粗、每段上色。长句拆成能独立理解的小项；清单拆分不能丢原条件。窄屏先显示当前节点，完整路线可按需展开，不让一整列进度占满首屏。

检查时除“没有溢出”外，还要确认第一眼能找到待确认点、执行顺序与主按钮。需由使用者实际反馈阅读是否舒适，作者自查不能代替体验确认。

### 本步核对：让人看懂后再给判断

按使用者对核对 tab 的进一步反馈，左侧不能只有分隔线与长段落。固定阅读顺序为：

1. **用来判断什么：** 用一个业务问题说明用途，紧接一句用途限制。
2. **规则怎么定：** 用“短标签 → 关键值 → 一句解释”呈现。指标展示统计对象、归月依据、去重依据，再用短流程说明计算；模型展示对象含义、身份和关系。按项目选择要核对的项，不能固定照搬示范三字段而漏掉关键口径。
3. **一例看懂：** 默认可见，用事件／输入到结果的对照讲清最容易混淆之处；说明来源、条件与是否实际运行。不要让使用者先展开详情才能知道怎么算。
4. **哪些仍待核：** 单列未知和影响，提供去查看具体业务问题的入口；不能把缺记录处理为零或让用户凭选项猜事实。

完整来源与范围细节可折叠，影响本次决定的范围、例外与未知仍放在可见区域。右侧继续留处理选项、自由意见和当前下一步；不将反馈当成业务确认。窄屏将规则卡与例子改成标签／值逐行排列，不缩小字号硬塞多列。此结构同步用于现有指标和业务模型样稿，尚未接入客户数据。

### 各模块共用：宽屏左右布局

按使用者已认可的方向，资料、访谈、模型、指标、测试验收和进度页面均使用同一层次。顶部交代本步与待确认点；桌面加宽，左侧放需要理解的内容，右侧放当前判断、待核和行动；详细依据按需展开。不是把文档机械切成左右两段，也不为填满宽度堆更多事项。

| 模块 | 左侧阅读区 | 右侧核对／行动区 |
| --- | --- | --- |
| 资料盘点与沟通提炼 | 已有材料、来源、提炼认识 | 缺口、补材料建议、本人待核 |
| 访谈与二次核对 | 找谁、先问什么、何时追问 | 最少带回的依据、取得限制、现场提纲 |
| 业务模型 | 对象关系、规则、场景与例子 | 采用建议、未知影响、本人意见 |
| 指标口径 | 含义、对象、时间、范围、算法与样例 | 关键核对点、处理选择、反馈与下一步 |
| 测试与验收 | 独立标准、实际结果、差异与证据 | 未测／失败／待确认、处理决定和验收责任 |
| 工作进度与交接 | 当前步骤、已完成成果与证据 | 本人当前需处理项、真实下一步与交接缺口 |

现有样稿的模型、指标和访谈视图已共用该布局，其余模块是生成页面时必须遵循的规范，并未在本轮开发成完整 UI 系统。宽度依屏幕扩展，样稿内容上限 1680px；内容列保持可读行长、字号和间距，不能只将文字拉长。宽屏以两列减少滚动，空间不足自动堆叠为先理解再处理；保留完整路线的展开入口，不用固定高度、截断内容或列内滚动伪造“更短”。导出的反馈放在对应操作区域，避免再次堆到全页底部。

| 区域 | 使用者看见什么 | AI 的责任 |
| --- | --- | --- |
| 当前节点 | 当前小步、为何做、做到哪、下一步是什么 | 技术完成、本人反馈、业务确认、实际签署分开；下一步沿流程，不自动推进 |
| 本步核对 | 业务含义、规则／算法、例子、来源、用途限制 | 模型展示对象关系规则；指标展示对象时间范围与算法；测试展示独立期望、实际及判定，未运行明确标出 |
| 处理建议 | 推荐动作、原因、影响、可选做法及自由意见 | 无事实依据时建议取证办法，不让用户猜事实；没有意见不视为通过 |
| 二次业务核对 | 已知什么、不清楚什么、找谁、怎么问、带回什么 | 沿 [09](../访谈/09-访谈准备与交接.md)复用缺口 ID，答复回来关联模型、指标、测试并核影响 |
| 来源与历史 | 摘要和精确定位，必要时看原文及旧版本 | 原话与 AI 解释区分；不要求先打开一堆 Markdown 才能理解当前事项 |

现场待问内容与内部备课解释分开；按角色只带本轮相关问题。真实资料留客户项目，不能放入公开工具包或无授权的托管服务。

## 交付前检查

- 页面与原记录同一项目／范围／版本，状态与来源对得上；数据缺失、旧版和未运行可见。
- 正常条目也有可读解释；关键未知不被“全部通过”掩盖。模型、指标和测试的结论分别呈现。
- 操作有明确反馈，未选择／未填写不默许通过，自由文字可用；修改意见有可追溯原话。
- 技术进度不随临时选择伪装推进；本人理解不变成业务确认或签署。
- 导出包含条目／版本／原话与草稿状态；换条目或修改意见后不能继续导出旧内容。
- 窄屏、键盘、长文字可用，来源可查看；页面反馈与真正保存／提交的能力如实说明。

这些检查验证阅读和交互，不证明业务模型、指标计算或 AI 执行已通过验收。
