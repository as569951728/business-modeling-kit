# 把验收结论变成可核查、可签署的材料

本章供业务模型和指标库共同使用，接 [12 模型验收](../建模/12-业务模型验收与完成判定.md)或 [15 指标验收](../指标库/15-验收与ETL交接.md)。它负责保存“这次交付了什么、依据是什么、谁确认了哪个版本”，不代替两类技术验收，也不自动取得客户签署。签署形式、责任人和确认范围沿用项目已有约定。

用户仍只需说“按工具包组织测试验收”。AI 从已有记录整理证据和签署材料，先交一页摘要；完整过程、索引和存档由 AI 维护。已有合同附件、验收单或归档平台可复用，不要求客户另用本包格式。

## 先看最终应交什么

一次验收交一份**带版本的验收证据包**，包含：业务可读的验收摘要／签署稿、验收项与证据对照、固定版本的交付与验证材料、遗留问题及处置依据、实际签署归档记录。可用[共用模板](../../templates/验收证据包与签署记录.md)，在现有验收记录中保留同等内容也可以。

签署稿应让业务方看懂：验收哪个项目／阶段、哪些能力和版本、依据哪份约定、哪些已达到、还有什么限制，以及本次确认的确切范围。技术细节放附件引用，不能只让对方签“测试通过”四个字。

对外签署稿只取业务摘要和约定的签署格式；AI 编制说明、本机工具包路径留在内部工作记录。对外交付索引使用包内相对路径或双方约定可访问的平台记录，不能把内部工作目录直接当作交付包。

## 必须留住的证据

| 类别 | 业务模型 | 指标库 |
| --- | --- | --- |
| 范围与标准 | 任务、场景、内容／使用验收层次、必须项及变更依据 | 指标清单、口径、维度／筛选、期间、环境、必须项及变更依据 |
| 业务依据与确认 | 原始材料、完整问答定位、候选取舍、关键定义与实际确认 | 模型／口径版本、字段及粒度依据、业务复核和未决规则 |
| 交付版本 | 模型、构建／提取方法、来源与未知记录 | 构建 Skill／逻辑、实际生成输入输出、指标定义与库、目录及依赖 |
| 独立标准与实际结果 | 有源测试与期望、加载／检索内容、真实请求回答、判读和所需对照 | 固定数据、测试集、expected_source、独立核算、judge 与自检、实际加载及问数／解释／trace |
| 问题与复验 | 原失败、修改理由、影响分析、复核与回归、遗留及处置依据 | 原失败、库／方法／数据变化、重新生成加载、回归、未覆盖及遗留 |
| 实际确认与签署 | 复核对象、人员与职责依据、日期、原始确认；签署记录绑定本次材料版本 | 同左，技术结论和业务签署状态分别保存 |

是否适用由本轮约定决定：只做模型内容验收时，实际运行列范围外并引用约定；本来要求使用验证却未运行，必须列缺证。演示截图可以辅助说明，不替代约定所需的原始运行与判读记录。

## 从验收条目追到原始证据

对每个项目验收项记录：**约定条目 → 对应模型／指标及交付版本 → 检查／用例 → 实际结果与证据 ID → 遗留问题 → 复核与结论**。AC／MA 编号只是工具包检查辅助，不能冒充客户已同意的合同条目。一个签署范围同时包含两类成果时，使用同一证据索引引用各自结论，分别保留未通过或待验证项。

每条证据登记实际文件／记录位置、来源与形成时间、版本或数据快照、支持的验收项、状态及访问方式。可校验的文件记录内容哈希，代码记录固定提交及必要产物哈希；可变分支名或“最新报告”不足以固定材料。哈希只帮助检查文件是否变化，不证明业务正确、运行真实或已签署。

## 固定材料与保存位置

默认存客户项目的 `验收/【批次或版本】/`，也可用已有归档目录／平台；在原项目入口登记位置，真实客户证据不进入公开工具包仓库。

1. **日常就留证。** 原件、运行目录、失败和修订记录随工作保存，验收时按索引收集，不在最后根据聊天补造日志。
2. **固定本次版本。** 给证据包一个稳定 ID／修订号和形成日期。保留已约定且可访问的不可变原记录；需要副本时保存相应快照。工作文件可以继续改，但签署所引用的快照不能随之覆盖。
3. **能打开、能核对。** 在约定接收环境检查附件及链接，不能只留编制者电脑上的绝对路径。外部系统记录保留稳定定位、适用版本、访问方式和保管人；无法访问或内容无法固定的证据列限制，不静默当满足。
4. **对外副本有对应关系。** 只包含该次交付需要且允许分享的材料。需要遮蔽敏感内容时保存内部原件与对外副本的对应关系，注明哪些内容未对外提供及如何按约定核验，不用脱敏副本替换内部原件。
5. **保管责任明确。** 记录保存位置、负责人、访问与保留约定；未约定的事项列待核，不自行设定保存年限或自动删除。不要为方便打包复制全部客户数据库。

目录形式不强制，重点是材料可追、版本固定、接收方能按约定核查。现有报告、签署平台可直接引用，不重复维护多份相互矛盾的材料。

## 三种状态分别记录

| 状态层 | 可以写什么 | 不能推定什么 |
| --- | --- | --- |
| 内容／技术验收结论 | 按 12／15 的实际证据写通过、未通过、待验证或需复验 | 有报告不等于业务已签署 |
| 签署材料准备 | 草稿、缺证待补、已复核可提交；写明本次范围与问题 | 已准备不等于已发送；存在关键缺证不能写整体验收通过 |
| 业务签署 | 未取得、待确认，或取得可核查记录后写已签署的具体范围 | AI 起草、口头认可或收到文件不自动等于正式签署 |

签署记录保存实际人员、角色／代表范围及依据、确认时间和方式、原始签署文件或可核查记录位置、绑定的证据包 ID／版本及保留事项。人员、日期、签名栏没有真实依据时留空或标待取得，AI 不代签、不伪造确认。若项目已有明确的确认机制，按它核验，不能自行推定某职位有权代表所有范围。

本包负责整理和留存。发送给业务方、发起签署、代替负责人确认，须有相应用户指令；“组织测试验收”本身不授权发送消息或代签。已经取得的有效范围内确认直接引用，不重复要求签署。

## 变更与收尾检查

提交后若改交付版本、标准、结果或重要遗留，保留旧包，形成新修订并记录差异和影响，按项目约定重新复核／确认；不能把旧签署记录直接附到修改后的成果上当作已签。签署后新增事项另记，不覆盖已签原件。

AI 提交摘要前，逐项检查：每个必须项有证据或明确缺口；交付／测试／数据／环境版本对应；全部适用原始运行、失败和回归可追；遗留处置有实际依据；附件可访问且快照固定；签署身份、范围和状态没有被猜填。只有材料达到本轮提交条件，才写“已准备可提交”；业务是否已签署始终看真实记录。

本章为项目交付与证据管理方法，不新增课程强制表单，不承诺任何材料自动产生签署或业务批准。当前工具包没有内置归档、哈希清单生成或签署服务，执行 AI 使用项目已有工具完成并核对。
